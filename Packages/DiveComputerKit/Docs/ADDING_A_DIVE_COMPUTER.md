# DiveComputerKit — adding a dive computer

As of 2026-11-20. Linked from `START_HERE.md`. A checklist for a session with no prior context; the code is the truth where this drifts. Paths are relative to `Packages/DiveComputerKit/` unless they start with `BlueDive/`, `BlueDiveTests/` or name a repository-root file.

Three cases, from the most common:

- **A.** A model of a family BlueDive already supports, which the vendored libdivecomputer already knows (no sync).
- **B.** A model that arrives with a libdivecomputer sync.
- **C.** A new protocol family (a `DC_FAMILY_*` BlueDive does not support yet).

Every case ends with "Definition of done" below. Rules that apply throughout (`START_HERE.md`, "Rules that bite"): no C patches, clean room (never read LibDCSwift sources), persisted formats never change, no data-model change, no personal data in the repository, and every change is owner-approved before it is made (CLAUDE.md).

## What is persisted (never rename, never reorder away)

| Value | Where it is persisted | Consequence |
|---|---|---|
| `ComputerModel.name` (`DeviceCatalog.supportedModels`) | `Dive.computerName`, `DeviceFingerprint.computerName`, Fingerprint XML, icon lookup (`DeviceIcon_<SanitizedName>`) | A renamed model orphans every dive and fingerprint stored under the old name |
| `DeviceFamily` raw value | `DeviceFingerprint.familyID`, Fingerprint XML `<familyID>`, `com.libdc.storedDevices` (`StoredDevice.family`, `BlueDive/Bluetooth/KnownDeviceStore.swift`) | A renamed case makes stored devices of that family undecodable (kept but unusable, see C.1) and fingerprints familyless |
| libdivecomputer model number (`ComputerModel.modelID`) | `DeviceFingerprint.modelID`, `StoredDevice.model` | Must equal the descriptor's `model` |
| First catalog entry per (family, model) | What `DeviceCatalog.model(family:modelID:)` returns: names shown for stored devices and fingerprints, `DiveImportContext.catalogComputerName` → `Dive.computerName` | A new sibling listed **before** an existing one with the same model number silently renames new downloads of the existing model |

`CatalogConsistencyTests.legacyModelsAreKept` enforces the first, third and fourth rows for the 116 models of the old library (`Tests/DiveComputerKitTests/Fixtures/legacy-catalog.json`, minus the 3 non-BLE models of `DECISIONS.md` Q4), `legacyFamiliesAreKept` the second (legacy families kept, new ones appended), `namesAreUnique` uniqueness. **Never edit `legacy-catalog.json` or `ble-name-samples.json`**: they are the old library's record, not a list to keep current. A model added after the cutover is protected only by review: treat its name as persisted from the first build that ships it.

## A. New model in a supported family, already in libdivecomputer

1. **Find the descriptor** in `Sources/CLibDiveComputer/src/descriptor.c` (`g_descriptors`): one row `{vendor, product, DC_FAMILY_*, model, transports, filter}`. Check:
   - `transports` contains `DC_TRANSPORT_BLE`. Without it the model is out of scope (`DECISIONS.md` Q4: BLE-only catalog); `everyModelHasBLEDescriptor` would fail.
   - `DC_FAMILY_*` maps to a `DeviceFamily` case (`Sources/DiveComputerKit/Catalog/DeviceFamily.swift`, `dcFamily`). If not, this is case C.
   - `model` (often hexadecimal: Oceanic/Pelagic two-character codes such as `0x4648`, Mares, Uwatec, Ratio) and whether another row of the same family has the same model number (siblings the protocol cannot tell apart, e.g. Tern / Tern TX, the OSTC models at `0x00`, Puck 4 / Lite / Pro EZ / Pro Ultra at `0x35`).
   - The filter (`dc_filter_<vendor>`, same file): whether it lists the advertised name per model or is family-wide. Shearwater, Suunto, HW, Mares and most others match a list of names or prefixes (`dc_match_name`, `dc_match_prefix`, `dc_match_prefix_with_number`) that accepts the name for **every** descriptor of the family; Oceanic/Pelagic (`dc_filter_oceanic`, `dc_match_oceanic`) list model codes; Cressi and Halcyon have their own matchers. `DescriptorLookup.firstBLEMatch` returns the **first** BLE descriptor whose filter accepts the name, so a family-wide filter resolves every model of the family to its first descriptor (step 3 handles this).
   If the product is not in the vendored `descriptor.c`, it is case B.
2. **Add the catalog row** to `DeviceCatalog.supportedModels` (`Sources/DiveComputerKit/Catalog/DeviceCatalog.swift`): `.init(name: "<vendor> <product>", family: .<case>, modelID: <descriptor model>)`.
   - Name: the descriptor's vendor and product joined by one space, trimmed (`"Shearwater Perdix 3"`, `"Heinrichs Weikamp OSTC Plus"`). When two rows would get the same name (same vendor and product, different model numbers), disambiguate as the catalog already does (`"Aqualung i200C (v2)"`); `namesAreUnique` checks this. The name is persisted from the first build that ships it: get it right before release.
   - Position: in the vendor's group (the `// Shearwater`, `// Mares`… comments; display order, although `ModelPickerSheet` sorts by brand and name). Keep every existing row in its relative order. **A model sharing a model number with an existing row goes after that row**; `legacyModelsAreKept` fails otherwise ("now resolves to … instead of …"). Otherwise any position in the group is fine.
   - Model number: copy the descriptor's exact value, in the same notation (hexadecimal where the descriptor uses it).
3. **Name resolution** (`Sources/DiveComputerKit/Catalog/BLENameResolver.swift`), only when the advertised name would otherwise resolve to the wrong model. Run `DeviceCatalog.resolve(advertisedName:)` / `displayName(forAdvertisedName:)` on the real advertised name in a scratch test (not committed) or reason through the four steps:
   - Step 1, Oceanic / Pelagic (`oceanicModel`): two printable characters + digits; resolves to any **catalog** model of `.oceanicAtom2` / `.pelagicI330R` with that code. Adding the catalog row is enough, provided upstream added the code to `dc_filter_oceanic` (the device's own handshake still needs it).
   - Step 2, Cressi (`cressiModel`): `"<model hex>_<hex>"`; catalog row enough.
   - Step 3, `prefixTable` (case-insensitive prefix, Mares and Seac): add an entry when the name carries no model code and the libdivecomputer filter is family-wide. Order matters: the **first** matching prefix wins, so a specific prefix goes before the generic one (`"Puck Pro U"` before `"Puck Pro"` before `"Puck"`; `"Smart Air"` / `"Smart Apnea"` before `"Smart"`).
   - Step 4, `patternTable` (case-sensitive, `.prefix` or `.substring`, names a descriptor by vendor/product), then the libdivecomputer filter: add a pattern for a family-wide filter, again specific before generic (`"Peregrine TX"` before `"Peregrine"`, `"Perdix 2"` / `"Perdix 3"` before `"Perdix"`, `"Petrel 3"` before `"Petrel"`, `"Luna 2.0 AI"` before `"Luna 2.0"`). A `.substring` pattern also matches longer names that contain it: check it does not capture another model's name.
   - The scanner lists only names that resolve (or devices already stored): `BluetoothScannerView.startScanning` filters with `DeviceCatalog.resolve`. A name that resolves to nothing never appears.
   - `NameResolutionTests` replays the old library's 141 resolutions (`ble-name-samples.json` → `legacy-catalog.json`): a new pattern or prefix must not change any of them. If one changes, the new entry is too broad: narrow it (do not edit the fixtures). The two `droppedResolutions` are the Q4 non-BLE models.
4. **Service UUID** (`Sources/DiveComputerKit/Catalog/BLEServiceCatalog.swift`, `knownServiceUUIDStrings`), only if the device's GATT service is not listed: lowercased 128-bit form, with a comment naming the vendor. The UUID comes from the backend's `.c` file or libdivecomputer's BLE notes, or from the device's `[BLE DISCOVER] Services:` line in a BLE diagnostic log (`TESTING.md`). Firmware-update services go to `excludedServiceUUIDStrings` instead. A vendor variant of the generic Nordic UART is preferred over it automatically (`BLECharacteristicSelector.preferredService`). `legacyServiceUUIDsAreKept` checks the old 14 are kept, no duplicate, all lowercased.
5. **Icon** (`DIVE_COMPUTER_ICONS.md` at the repository root): a 132×132 PNG imageset `BlueDive/Assets.xcassets/DeviceIcons/DeviceIcon_<SanitizedName>.imageset` (`modelLevelAssetName` in `BlueDive/Bluetooth/BluetoothScannerComponents.swift`: `Heinrichs Weikamp` → `HeinrichsWeikamp`, other non-alphanumerics → `_`, e.g. `"Shearwater Perdix 3"` → `DeviceIcon_Shearwater_Perdix_3`). Without one, the brand icon is used (`assetName(forName:)`); a new **vendor** also needs a brand keyword there (mind the order comment: `"oceanic"` before `"oceans"`, `"deepblu"` before any `"deep"`) and a brand imageset. Use only images the owner may redistribute.
6. **App surfaces to check** (nothing to change for most models):
   - `ModelPickerSheet` (`BluetoothScannerComponents.swift`) groups by the name's first word, or the first two for `["Deep Six", "Heinrichs Weikamp"]`: a new two-word vendor must be added there.
   - "Filter unused tanks" (`DiveImportMapper.familiesNeedingSwiftTankFilter`) is per family; a new model of a listed family is covered.
7. **Tests**: `swift test` in the package (all suites; `CatalogConsistencyTests` and `NameResolutionTests` are the catalog checks: every model has a BLE descriptor, every BLE descriptor of a supported family is in the catalog, legacy models/UUIDs kept, unique names, legacy resolutions unchanged). Then the golden and mapper parity runs and both app builds ("Definition of done").

## B. New model from a libdivecomputer sync

1. Follow `Sources/CLibDiveComputer/UPSTREAM.md`, "Sync procedure", steps 1–4 (clone, copy, `version.h`, `diff -r`).
2. Step 5 (review the C diff): list the new descriptor rows and filter changes in `descriptor.c`, plus any new `DC_FAMILY_*` (case C), `DC_IOCTL_*`, sample, field or event types, and iostream behaviour (`purge`, `sleep`, timeouts) the new backend relies on.
3. Run `swift test`: `CatalogConsistencyTests.everyBLEDescriptorIsInCatalog` (the tripwire) fails once per new BLE descriptor of a supported family and names it (`"<vendor> <product> (<family>, 0x<model>) is missing from DeviceCatalog"`). A new BLE descriptor of an **unsupported** family is skipped by the tripwire: decide with the owner whether it is case C.
4. Apply case A to each named descriptor (catalog row, name resolution, service UUID, icon).
5. Record the upstream commit that added each model in UPSTREAM.md's "Changes since the previous snapshot" table, and finish the sync procedure (steps 6–10: builds, golden parity, mapper parity, UPSTREAM.md, device smoke test). The sync is its own commit (`chore: sync libdivecomputer to <short sha>`); the catalog rows can be part of it or follow in a separate `feat:` commit, as the owner prefers.

## C. New family

Decide with the owner first: a family is a protocol, with its own transport behaviour, parser output and per-family app rules.

1. **`DeviceFamily` case** (`Sources/DiveComputerKit/Catalog/DeviceFamily.swift`): a new case with a lowerCamel raw value in the existing style (`<vendor><Model>`, e.g. `seacScreen`), **appended at the end** (`allCases` order is checked), plus its `dcFamily` mapping. `init?(dcFamily:)` derives the reverse mapping from `allCases`, so nothing else is needed for "both ways"; check that no other case maps to the same `DC_FAMILY_*`.
   - `legacyFamiliesAreKept` requires the old library's 16 families to be a prefix of `allCases`, unchanged and in order, so an appended family passes; it also checks that raw values and `dcFamily` values are unique. Do not edit `legacy-catalog.json`.
   - **Known devices from this build on** (`DeviceStorage`, `BlueDive/Bluetooth/KnownDeviceStore.swift`): an entry of `com.libdc.storedDevices` that does not decode (a family added by a newer build) is skipped on read, and every write puts it back after the readable entries, unless the write has an entry with the same `uuid` (which replaces it); `removeDevice(uuid:)` removes it. Such an entry is kept by value (re-serialized), not byte for byte. Only whole entries survive: a field added to `StoredDevice` must be optional, and an older build's save drops it from the entries it can read. This build can neither show such an entry nor see its serial, so the serial sweeps (`removingOtherIdentifiers`) never remove it. Deleting a known device in an older build cannot remove an entry it cannot read (its serial is not visible to the serial sweep), so that entry and its Keychain access code survive until the newer build removes it. A blob whose top level is not a JSON array still reads as no device. `KnownDeviceStoreTests` covers these rules.
   - **Builds before that change (2.1 and 2.2) still wipe the list**: they decode the whole array with `try?`, so one entry with an unknown family makes them see no stored device, and their next save rewrites the list without it. No separate key is needed for that (`DECISIONS.md` L6): a new family's devices go in `com.libdc.storedDevices` like the others, because App Store users can never run an older build over a newer one (updates only move forward, on iOS and macOS). Only a TestFlight tester going back to a build older than 2.2.1, or an older branch run from Xcode, can hit the wipe, which a rescan repairs; say so in the TestFlight notes of the build that adds the family. `DeviceFingerprint.family` is nil on an older build (`familyID` is kept as a string, so the record survives, and syncs through iCloud to devices still on an older build).
2. **Catalog rows, resolution, service UUID, icon**: case A, steps 1–5, for every BLE descriptor of the family (the tripwire now covers the family). If the family's names follow a scheme the four resolver steps cannot express, a new step in `BLENameResolver.resolve` is a design change for the owner.
3. **Transport and session**: read the backend's `<vendor>_<model>.c` for what it asks of the iostream: `dc_iostream_purge`, `dc_iostream_sleep`, `dc_iostream_set_timeout`, `dc_iostream_poll`, packet sizes, and ioctls. `DCIOStream` / `DCIOControl` (`Sources/DiveComputerKit/IOStream/`) already answer `DC_IOCTL_BLE_GET_NAME`, `CHARACTERISTIC_READ`, `GET_PINCODE`, `GET_ACCESSCODE` and `SET_ACCESSCODE`; any other request returns `DC_STATUS_UNSUPPORTED` (logged `[BLE IOCTL] Unsupported request`). A new ioctl needs a shim accessor (`Sources/CLibDiveComputer/shim/dc_shim.c` and `Sources/CLibDiveComputer/include/dc_shim.h`, BlueDive's own files) and a case in `DCIOControl.handle`. Change `BLETiming` only with a device test and a BLE diagnostic trace (`DECISIONS.md` L5 shows the expected record). Write the family's behaviour into `DECISIONS.md` if it needs a rule.
4. **Pairing** (PIN / access code): the session passes `BLEPairingProvider` (`BlueDive/Bluetooth/BLEPairingProvider.swift`) for every family, so the ioctls work as soon as the backend calls them: the PIN prompt (`BLEPairingPrompt`, shown by `BluetoothScannerView`), the access code in the Keychain (`BLEAccessCodeKeychain`, keyed by advertised name, deleted with the stored device in `KnownDeviceStore.swift` and `BluetoothScannerView+Import.swift`). Check that the family's advertised name is stable (it is the Keychain key), that a 6-digit PIN and a 16-byte access code match what the backend expects (`DCIOControl`: `getAccessCode` requires `code.count == size`), and the user-facing texts, which name Aqualung i330R / Apeks DSX (`BluetoothScannerView.swift`, the PIN prompt; `BluetoothScannerView+BLE.swift`, the refused-connection error) — a changed string needs the translation workflow (CLAUDE.md).
5. **Parser family rules** (`Sources/DiveComputerKit/Parsing/DiveParser.swift`), from the backend's `<vendor>_<model>_parser.c`:
   - `reportsSetpointEverySample`: true when the parser emits `DC_SAMPLE_SETPOINT` on every sample of a CCR dive and nothing on open circuit (Shearwater, DiveSystem, McLean); false when it emits it only on a change (then the setpoint is held from the gas mixes' diluent/oxygen usage, `SampleAccumulator`). Add the case to `FieldRuleTests.setpointFamilies` (`Tests/DiveComputerKitTests/ParserTests.swift`).
   - Shearwater-only rules (`isShearwaterPNF`, the maximum depth taken from the samples for legacy logs) and the Uwatec rule (`dropUwatecDefaultRBT`): check whether the new parser has a similar quirk (a placeholder value sent before real readings, a field rounded to whole units) and add a rule with a `FieldRuleTests` / `SampleAccumulatorTests` case only if it does.
   - Fields and samples: `FieldReader` reads `DC_FIELD_DIVETIME`, `MAXDEPTH`, `AVGDEPTH`, `GASMIX_COUNT` / `GASMIX`, `TANK_COUNT` / `TANK`, `SALINITY`, `ATMOSPHERIC`, `TEMPERATURE_*`, `DIVEMODE`, `DECOMODEL`; `SampleInput.init(type:value:)` maps `DC_SAMPLE_TIME` … `DC_SAMPLE_LOCATION`, anything else is `.ignored`. List the `DC_FIELD_*` the parser's `get_field` supports and the `DC_SAMPLE_*` it emits; a type BlueDive does not read yet is new parser work (`SampleAccumulator`, `DiveData`) and a decision for the owner.
6. **App mapper rules** (`BlueDive/Bluetooth/DiveImportMapper.swift`, `MAPPER.md`):
   - `familiesNeedingSwiftTankFilter`: add the family when its parser reports every configured gas slot (or no `DC_FIELD_TANK`) even when unused, so "Filter unused tanks" removes the phantom tanks. Then update the Settings caption that lists those brands (`BlueDive/SettingsView/BluetoothSettingsView.swift`, the text under "Filter unused tanks"; a changed key needs the translation workflow) and `DiveImportMapperTests.theFilterAppliesOnlyToFamiliesWhoseParserKeepsUnusedMixes`.
   - Gas/tank inference when a tank's mix is `DC_GASMIX_UNKNOWN`: `resolveGasMix` has Shearwater (tank N = mix N), Halcyon (oxygen tank by composition, no profile-order tier) and a profile-order tier for the others; `buildTanksFromComputerTanks` has the Shearwater pressure-guided inference (`inferShearwaterGasMixToTank`). Decide which tier fits the new family's tank/mix numbering and add a `DiveImportMapperTests` case with made-up data.
7. **Every other `DeviceFamily` use** (grep `DeviceFamily` and `\.<case>\b` in `BlueDive/` and `Sources/` to refresh this list). As of 2026-11-20, beyond the above: `BLENameResolver.oceanicModel` (Oceanic/Pelagic only), `DiveParser.parse` (Uwatec, Shearwater), `DeviceSession.openDevice` (falls back to the name's family when a stored/forced one fails to open: generic), `DeviceFingerprint.family` and `FingerprintImportFlow` / `FingerprintXMLExporter` / `FingerprintXMLParser` (raw value as a string: generic), `StoredDevice` (Codable: see step 1), `BluetoothScannerView+Import.swift` (fingerprint identity: generic), `DiveImportMapperParityTests` (reads `familyID` from the fixtures: generic). No `switch` over `DeviceFamily` exists in the app; the package's only exhaustive one is `dcFamily`.

## Validating without owning the unit

The owner's units are a Perdix 2, a Perdix 3, a Peregrine and an i300C (`TESTING.md`, "Device test matrix"). For anything else:

1. **Ask a beta tester for a BLE diagnostic log** (Settings → Bluetooth Import → BLE Diagnostic Logging, then Save Diagnostic Log; `TESTING.md`, "Reading a BLE diagnostic log") of a download with the new build, and a **BlueDive XML export** of the downloaded dives (raw computer data included). Ask, if possible, for screenshots or values from the computer's own logbook (or the vendor's app) for two or three dives: maximum depth, duration, temperatures, gases.
2. **Check** in the log: the chosen service and characteristics, the open, `Fingerprint … DC_STATUS_SUCCESS`, `Download ended with DC_STATUS_SUCCESS`; in the export: the computer name, serial, duration, depth, gases and tanks against the computer's logbook.
3. **Golden parity does not apply.** Golden files come only from the external harness running the **old** LibDCSwift (`GOLDEN_FORMAT.md`, `START_HERE.md`, "Private data"); a model or family the old library did not support has no golden, and goldens are never generated with DiveComputerKit (the test would compare the code with itself). Instead:
   - pin the family's rules with unit tests on **made-up data** (`SampleAccumulatorTests` / `FieldRuleTests` with scripted sample streams, `DiveImportMapperTests` with a constructed `DiveData`), never with a tester's dive (CLAUDE.md, "No Personal Information in the Repository");
   - compare the parsed result with the computer's own logbook (step 2);
   - keep any real file (log, export) outside the repository, under `~/BlueDive-Fixtures/traces` or `~/BlueDive-Fixtures/exports` at most, and never quote serials, names or dive values from it in code, docs or commit messages. A test that reads such a file is local only and never committed.
4. **Record the result** in `TESTING.md`'s device test matrix (model, family, "A beta tester, device", date, result, notes without personal data) and remove the model from the "No device test and no golden" list.

## Definition of done

- [ ] The app builds for an iOS destination and **My Mac** (CLAUDE.md).
- [ ] `swift test` in `Packages/DiveComputerKit` passes (catalog, name resolution, parser rules).
- [ ] Golden parity passes for every set (`DCK_GOLDEN_DIR`, `TESTING.md`) and mapper parity plus `DiveImportMapperTests` pass (`BLUEDIVE_PARITY_DIR`).
- [ ] The catalog name is final (persisted); a sibling sharing a model number is listed after the existing one.
- [ ] Icon imageset added, or the brand fallback checked (new vendor: brand keyword and `ModelPickerSheet` grouping).
- [ ] Changed user-facing strings translated (`Scripts/xcstrings.py`, CLAUDE.md).
- [ ] `TESTING.md` device matrix updated once tested.
- [ ] From a sync: UPSTREAM.md "Changes since the previous snapshot" lists the upstream commit.
- [ ] No personal data in code, tests, docs or the commit message.
