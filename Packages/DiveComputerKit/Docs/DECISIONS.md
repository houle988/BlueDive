# DiveComputerKit — Owner decisions

Decisions taken by the project owner on 2026-11-02 in answer to the open questions of `ARCHITECTURE.md` §9. Where a decision differs from the architecture document, **this file wins**.

| # | Question | Decision | Consequence for the design |
|---|---|---|---|
| Q1 | Static or dynamic linking of the LGPL libdivecomputer target | **Static** | `CLibDiveComputer` stays a static target. LGPL §6 is met by publishing the complete libdivecomputer source in the repository and by adding a relinking clarification to `LICENSE` (wording to be drafted in Phase 6 and approved by the owner before it is written). In-app licence notice required (About → Licences). |
| Q2 | Allow cancelling a download | **Yes** | Add a Cancel button in the downloading state, `DeviceSessionHandle.cancel()`, new localized strings (fr-CA, de, nl, nb, es). `isTeardownUnsafe` was meant to be reduced to `.importing` only; the owner kept it as it was (2026-11-06): the Bluetooth sheet still cannot be closed while connecting or downloading, and the way out of a download is the Cancel Download button. |
| Q3 | Commit golden files and BLE traces (personal dive data) | **No — they stay private** | Goldens and traces live outside the repository; tests read them from the `DCK_GOLDEN_DIR` / `DCK_TRACE_DIR` environment variables and are skipped when the variables are unset. *As built: only `DCK_GOLDEN_DIR` (golden parity) and the app's `BLUEDIVE_PARITY_DIR` (mapper parity) exist; trace replay was not implemented (`ARCHITECTURE.md`, "As built").* *As built (2026-11-19): the bundled fixtures folder is `Tests/DiveComputerKitTests/Fixtures/` (`Package.swift`: `.copy("Fixtures")`, so anything in it is copied into the test bundle); it holds only the committed, non-personal `ble-name-samples.json` (advertised-name samples) and `legacy-catalog.json` (the old library's catalog and name resolutions). The package `.gitignore` ignores `golden*/`, `traces/`, `mapper-parity/`, `exports/` `*.log` / `*.bluedive` / `*.xml` under it, and a loose `manifest.json` or golden file (`<serial>_<sha16>.json`) dropped directly in it, as a safety net only. Private data stays in `~/BlueDive-Fixtures` (layout: `START_HERE.md`), passed by environment variable, never inside the package.* Only synthetic fixtures are committed. |
| Q4 | Keep the non-BLE legacy catalog entries (Atom 3.1, Wisdom 3, Icon HD) | **No — BLE devices only** | **Overrides `ARCHITECTURE.md` §4.1**, which kept them for display-name compatibility. `DeviceCatalog.supportedModels` contains only models whose libdivecomputer descriptor has `DC_TRANSPORT_BLE`. `CatalogConsistencyTests` enforce it in both directions. Existing dives keep their stored `computerName` string, so nothing already in the logbook changes. |
| Q5 | Ship the Pelagic i330R / Apeks DSX PIN prompt in this cycle | **Yes — now** | `BLEAuthorizationProvider` is implemented by the app: PIN prompt (`DC_IOCTL_BLE_GET_PINCODE`, 6 digits, asked synchronously from the libdivecomputer thread through a MainActor continuation; *as built: a semaphore the main-actor prompt signals, `BLEPairingProvider`*) and access-code persistence (`GET_ACCESSCODE` / `SET_ACCESSCODE`, 16 bytes). Moves from optional Phase 6 into Phase 4 (package) and Phase 5 (app UI and strings). Access-code storage must not be a SwiftData model change. |
| Q6 | Branch and PR structure | **This branch (`working-2.1-BLE`)**, temporary local commits between phases | One phase per local commit, made only when the owner asks. No pushes, PRs or tags without explicit authorization (CLAUDE.md). |
| — | Package location | **`Packages/DiveComputerKit/` at the repository root** | `BlueDive/` is an Xcode synchronized folder (pbxproj:96), so a package under `BlueDive/Bluetooth/` would be compiled into the app target as well. App-side files (`KnownDeviceStore`, `DiveImportMapper`, `BluetoothSyncController`) live in `BlueDive/Bluetooth/`. *As built: `KnownDeviceStore.swift` (types `DeviceStorage` / `StoredDevice`) and `DiveImportMapper.swift`; no `BluetoothSyncController` (`ARCHITECTURE.md`, "As built").* |

| L4 | **Gas mixes that cannot be read keep the others in place.** `DiveData.gasMixes` holds only readable mixes; when one is missing, `gasMixFieldIndices` gives each one's `DC_FIELD_GASMIX` index and `DiveImportMapper` turns every gas reference into a position first (a reference to the missing mix becomes unknown). The diluent/oxygen sets of change-only setpoint families use the field indices. No effect when every mix reads. | 2026-11-07, review fix |
| L5 | **`purge` discards unread input, once the device is quiet.** On the input bit (also set by `DC_DIRECTION_ALL`), `BLEPeripheralLink` waits on its condition until no notification has arrived for `BLETiming.purgeQuietPeriod` (0.15 s), at most `purgeQuietMaximum` (1 s), ending early on a cancel or a disconnect, then drops the queued notifications and logs the bytes dropped (only when there were some; libdivecomputer logs every purge itself). An idle link is not waited for, so the open-time purges cost nothing. Output does nothing (CoreBluetooth cannot withdraw a queued write); SUCCESS for any direction. Former bridge: NULL (no-op). **Why:** upstream `14f9293` retries a failed i330R/DSX flash read with a 1 s sleep then a purge, which left the abandoned reply in the queue. Of the 16 BLE families, the retry purge (after the backend's own sleep) matters for oceanic_atom2 (i300C…), mares_iconhd, seac_screen and pelagic_i330r; 13 families also purge at every `dc_device_open` attempt (`purge(ALL)` before their first write, up to `BLETiming.openAttempts` times per link; not Pelagic i330R, EON Steel, Divesoft). Every purge precedes a write, so only the failed exchange's bytes can be dropped. **Why the quiet wait** (added after review, before the device test): oceanic_atom2 increments its command sequence only on success, so before this change a late but complete reply was accepted by the resend; an immediate clear 100 ms after the timeout could cut a multi-notification reply still arriving (big-page models: i770R, A300CS, ProPlus X, F11, ProPlus 3) and its tail failed the resend's header/sequence check, possibly on both retries. With the wait the late reply arrives whole and is dropped whole, and the resend reads its own reply. Seac skips bytes up to the next start byte (`0x55`), so a cut tail there is usually skipped with a warning. A reply still arriving after 1 s is still cut. **First-read floor:** `BLETiming.firstReadFloor` now ends when a read first returns data (`readReturnedData`, was: when the first notification arrived), so notifications a purge drops unread (a stray one before an open-time purge, or a late reply dropped before open attempt 2 or a retry) no longer take the floor away from the reply the backend reads. Without a purge it ends as before; when nothing was ever read, the exit-command read of a close without a cancel gets the floor too (after a cancel, reads stay capped at `closeAfterCancelReadLimit`, 1 s). **Not ruled out:** a device that answers a command late and ignores its resend loses that late answer to the purge (before, it answered the retry); in a BLE trace, a `Purge: N unread bytes discarded` line followed by a read timeout is that case. A late reply whose first notification arrives only after the purge (the link was idle, so nothing was waited for) is read by the resend as before (Oceanic accepts it, the sequence being unchanged). During the close after a cancel the wait still applies, so an Oceanic exit command retried by the backend can take up to 1 s more per retry (bounded; `prepareForClose` has already waited for quiet). That nothing a backend needs arrives unsolicited before the open-time purge is checked in the C code for every family, but observed only on the owner's devices (Shearwater, i300C); for Deepblu, Oceans S1, Halcyon, Deep Six and McLean it is an inference. **Tests:** the parser is untouched (golden parity cannot see the transport); `TransportSessionTests` checks the purge calls and their order with the real Oceanic backend over `FakeLink`, which cannot exercise the quiet wait; the device test and a BLE trace cover the link. This adds two `BLETiming` constants and changes when another applies, hence the device test and BLE traces recorded in the status column (i300C: the first read still waited 5 s; every open-time purge dropped nothing). **Open:** a trace from a big-page Oceanic user (quiet wait on a real late reply) and from an i330R/DSX user. Follow-up only if traces call for it: discard unread input before open attempts 2–5 for families that do not purge at open. | 2026-11-13, owner approved; device-tested 2026-11-13/14 (Aqualung i300C: open, first-read floor and retry purges, 78 dives; Shearwater Perdix 2 and Perdix 3, protocols V1 and V2: open purge, 23 and 30 dives; nothing dropped, nothing slower) |
| L6 | **No separate known-device key for new families.** A device of a family added after the cutover (the first one expected: Suunto Nautic / Ocean, libdivecomputer PR #73) is stored in `com.libdc.storedDevices` like every other family; there is no `com.libdc.storedDevices.v2` layer. This supersedes the earlier plan in `ADDING_A_DIVE_COMPUTER.md` C.1. **Why:** only an older build on the **same** device can read that key (UserDefaults is per device and not synced), and App Store users cannot get one: App Store updates only move forward on iOS and macOS, offloading or restoring from a backup reinstalls the current version, and deleting the app erases UserDefaults. A user who stays on 2.2 or earlier never gets the build that stores a new family, and every build from 2.2.1 on keeps the entries it cannot decode (`b21ab2e`). **Remaining exposure, accepted:** a TestFlight tester who installs a build older than 2.2.1 from TestFlight's previous builds, and the owner running an older branch from Xcode on the same device or Mac. Such a build sees no stored device and its next save rewrites the list without the new family's entries (the older entries are lost too). This is recoverable: dives and watermarks are in SwiftData, Pelagic access codes in the Keychain, and a tap on a known device scans and stores it again; a model the user picked by hand must be picked again. `seedDeviceStorageFromDatabase` skips `modelID == 0`, so a device whose model number is 0 (e.g. Suunto Nautic, EON Steel) is restored only by that rescan, not from its `DeviceFingerprint`. When a build with a new family goes to TestFlight, its notes say not to go back to a build older than 2.2.1. | Decided 2026-11-22 (owner) |
| L7 | **The watermark is still saved after a partial download.** When a download ends with `DC_STATUS_PROTOCOL` after some dives were delivered, the newest delivered dive's fingerprint is saved (`DownloadDecision.decide`, `.protocolError where f.hasNewDives`, unless the user chose "Download all dives"), as the former library did (`BEHAVIOURAL_SPEC.md` §5.3). A timeout, an I/O error or a disconnect saves nothing. **Consequence:** dives are delivered newest first, so the older dives that were not delivered are skipped by the next incremental downloads; "Download all dives" recovers them, and the duplicate check drops the dives already in the logbook. Reviewed for Suunto Nautic / Ocean (libdivecomputer PR #73), whose driver stops at the first failed dive so that a newer dive's fingerprint cannot mark it as downloaded: there, most failures (a link drop, the Suunto app taking the link) end with a timeout or a protocol error within a few seconds; the guidance text for Suunto users explains when to use "Download all dives". | Decided 2026-11-22 (owner): keep |
| L8 | **Suunto Nautic S gets its own catalog name, "Suunto Nautic S".** The watch cannot be told apart from a Nautic with PR #73 as written: it advertises `Suunto Nautic <serial>`, `/Info` gives the model name "Nautic" (only its codename differs: `Ylivieska`; Nautic `Vaasa`, Ocean `Porvoo`), the driver never sets `devinfo.model` (always 0) and `descriptor.c` has no Nautic S row. A catalog row sharing model 0 with the Nautic would never be returned (`DeviceCatalog.model(family:modelID:)` returns the first), and a BlueDive-only model number is not allowed (the catalog model must be the descriptor's). **Approach:** ask upstream, before the PR is merged, to report the model from the `/Info` codename (e.g. Nautic 0, Ocean 1, Nautic S 2) and add a `{"Suunto", "Nautic S", DC_FAMILY_SUUNTO_NAUTIC, …}` descriptor; BlueDive then adds an ordinary catalog row after "Suunto Nautic" (case B). Rejected: guessing from the dive data in Swift (the Nautic S writes the Ocean's 141-byte status record, the Nautic 195 bytes; fragile across firmware, known only after the first dive, needs a resolver step that names a catalog row instead of a descriptor) and a manual model pick (needs its own model number). **The family does not ship before this is settled:** the name is persisted (`Dive.computerName`, `DeviceFingerprint`), so Nautic S dives downloaded by a build without it would keep "Suunto Nautic". | Decided 2026-11-22 (owner); pending upstream |
| L9 | **The scan also lists dive computers already connected to the system.** A peripheral holding a connection stops advertising, so `didDiscover` never sees a computer another app holds (LightBlue, nRF Connect, a vendor app). Apple: `retrieveConnectedPeripherals` returns the peripherals connected to the system, which "can include those that other apps have connected". It does not help a computer that stopped advertising on its own: after LightBlue disconnected, the Perdix 2 did not advertise again and was not listed, before or after this change (no `[BLE SCAN]` line: the system no longer held a link), until Bluetooth was turned off and on on the Perdix itself; the same follows BlueDive's own close (its exit command ends the computer's Bluetooth). Each `BLECentral.scan` now also calls `retrieveConnectedPeripherals(withServices: BLEServiceCatalog.knownServiceUUIDs)`; the results go through the same rule as advertisements (`DiscoveryTable.register`: a name is required, the discovery filter is asked only for a new identifier, the list is published only when a device is new) and are logged `[BLE SCAN] Already connected to the system: <name> <uuid>, state <state>`. Once per scan, no timer: a computer connected after the scan started appears after a rescan. The known-device path already reached such computers (`retrievePeripherals(withIdentifiers:)`) and is unchanged. **Not ruled out:** a retrieved peripheral carries its GAP name, which may differ from its advertised name (the known-device path has the same); it is found only if the system has discovered its services (LightBlue and vendor apps do); if the other app is active on the computer (e.g. syncing), both command streams share the one link and the download fails or stalls (the user closes the other app). Our close ends our own connection; whether the other app keeps its link depends on the computer: the Shearwater exit command sent by the close (also after a cancel) returns the computer to its main screen and ends Bluetooth, which disconnects the other app too (observed with LightBlue); a computer without an exit command would leave the other app connected. **Tests:** `DiscoveryTableTests` (the rule, without CoreBluetooth); device test in `TESTING.md`. | 2026-11-22, owner approved; device-tested 2026-11-22 on macOS (Shearwater Perdix 2 held by LightBlue: not listed before the change; after it, listed by the `[BLE SCAN]` line 1 ms after the scan started, state `disconnected`, then opened over the shared link, identified and downloading until cancelled; the cancel's exit command returned the Perdix to its main screen and also disconnected LightBlue). Aqualung i300C (oceanicAtom2, bonded at the OS level), 2026-11-22, macOS: held by LightBlue when the scan started, listed by the `[BLE SCAN]` line, its GAP name (the Pelagic model code and serial) still resolving to the i300C, then opened over that link and downloading until cancelled; after LightBlue disconnected it advertised again and was found and opened through its advertisement (the unchanged path); a complete download while LightBlue held it (connected, idle) finished with 7 dives imported, no read or write error, and the watermark saved. Aqualung i300C on iPadOS, 2026-11-22: connected by the system through its pairing, with no app holding it: listed by the `[BLE SCAN]` line as the scan started, opened over the system's link and downloading (one dive) until cancelled. Retested 2026-11-22: a Perdix 2 just released by LightBlue is not listed (it stops advertising; Bluetooth must be restarted on the computer). Not yet tested: a Suunto watch held by the Suunto app or the system, the Pelagic i330R / DSX access code (kept in the Keychain under the advertised name; a retrieved peripheral carries its GAP name, so a different GAP name would ask for the PIN again), and the families whose identity depends on the exact name format (Cressi `<hex>_<hex>`, Ratio / DiveSystem, Halcyon: if the GAP name differs, the computer is not listed, never resolved to a wrong model) |

## Phase 4 implementation notes (2026-11-02)

Behaviour kept from the former bridge unless listed here:

| Change | Why |
|---|---|
| CoreBluetooth runs on a private queue, not the main queue; every wait is an `NSCondition` wait with the spec's timeouts instead of 50 ms / 1 ms polling | Removes the main-queue deadlock class; same timeouts |
| No auto-reconnect after an unexpected disconnect; the session fails with `SessionError.disconnected` | Source of the double-free and Shearwater 30 s hang bugs (`ARCHITECTURE.md` §4.2) |
| `didFailToConnect` and a disconnect fail waits at once (were: the 30 s / read timeout ran out) | Deterministic errors |
| Download cancellable at any time (`DeviceSessionHandle.cancel()` waits for teardown) | Q2 |
| After a cancel, the device is still closed normally: `SessionLink.prepareForClose()` (before every close; a cancel arriving during the close then only shortens reads) lets `dc_device_close` send the protocol's exit command (libdivecomputer disables cancellation for the close), after waiting until the device has sent nothing for 150 ms (at most 1 s) and dropping what it left unread; reads during the close limited to 1 s; then the link is cut | On the Perdix 3 the disconnect alone already ended the transfer (2026-11-06, the BLE icon stopped blinking); the exit command covers computers that would otherwise stay in transfer mode until they time out. The quiet wait was added after the i300C, cancelled mid-answer, sent one more 18-byte piece that libdivecomputer read as the exit command's reply (the i300C still returned to its normal screen) |
| PIN / access-code ioctls answered through `BLEAuthorizationProvider` (no provider = unsupported, as before) | Q5 |
| A dive is parsed with the model the device reports and, only if libdivecomputer has no descriptor for it, with the opened descriptor's model (was: the dive was skipped) | Only affects dives the old code dropped |
| Fingerprints come from `SessionRequest.fingerprintsBySerial`; no UserDefaults fingerprint store | SwiftData is the single source of truth |
| libdivecomputer's `poll` callback stays unimplemented (a no-op), as before | Parity; changing it is a separate step with device tests |
| `purge` was a no-op here too; it now discards unread input (L5) | Upstream `14f9293` relies on it before retrying an i330R/DSX flash read |
